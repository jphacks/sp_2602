# 新しい Issue を立てる（スコープを膨らませない）

方針: **見つけたものは今のコードに入れない。Issue にして、今の Issue を小さいまま完了させる。** 立てる前に必ず人間へ下書きを見せて確認を取る（勝手に作らない）。

## 1. 今の Issue に入れるか、別にするかを決める
次の順に判定する。

| 問い | はい | いいえ |
|---|---|---|
| 今の Issue の「完了条件」を満たすのに、これが**必須**か | **ブロッカー**。種類 `blocked`、今の Issue が新 Issue に依存する（手順 3 へ） | 次の問いへ |
| 今の Issue の完了条件に**もともと書いてある**か | 今の Issue でやる（別 Issue にしない） | 別 Issue にする |

- 「ついでに直せる」「数行で済む」は理由にならない。完了条件に無ければ別 Issue。
- 迷ったら別 Issue にする。MVP を優先し、後で削る・後回しにするのは Issue 側で決める。

## 2. 重複を確認する（立てる前に必ず）
```bash
npm run issue -- <種類> <宛先id> "<題名>" --dry-run
```
- 似た open な Issue があれば止まる。**新しく立てず、そちらにコメントする**（先頭に `<自分のid>:`）。別件のときだけ `--force`。
- 宛先は「対応する人」の id（自分ではなく、直す・決める人）。自分の担当の後回しなら自分の id。他人の担当部分なら担当者（`docs/members/`）。契約の追加・変更は `change-request` で lead。

## 3. 下書きを作って、人間に見せる
粒度は **1 Issue = 1 作業単位（30 分程度で終わる）**。見積もりが 30 分を大きく超えるなら、単体で動作・テスト確認できる機能単位に分けて、それぞれ下書きにする。
- 分け方の目安: 「画面を表示する」「利用時間を取得する」のように、1 つの動作を確かめられる単位。「〜周り全般」「〜の整備」のような大枠にしない。
- 分けると完了条件のテストも小さくなる。分けても 1 件ずつテストを持たせる。

本文のひな型（ファイルに書く。引数で渡さない）:
```markdown
## 概要
<何が問題・追加なのか。1〜3 文>

## 発見の経緯
<どの Issue（#N）のどの作業中に見つけたか>

## 完了条件
- [ ] <動作の条件>
- [ ] <テスト: 単体テスト、または確かめる手順（コマンドと期待する結果）>

## 参考
Depends on #<先に終わるべき Issue>   ← 依存があるときだけ
```
- 依存は向きを決めて書く: ブロッカーなら新 Issue には依存を付けず、今の Issue 側に足すようコメントで知らせる。後回しの追加案なら新 Issue に `--blocked-by <今の Issue>` を付ける。
- 完了条件に**テスト（または確認手順）を必ず入れる**。入れられないものは Issue にしない。

人間への見せ方（1 件ずつ「〜のため、…を立てる」の形で）:
```
題名: …
種類 / 宛先: <種類> → <宛先id>
理由: 今の Issue（#N）の完了条件に無い／ブロッカーではないため別にする
依存: <あり／なし>
重複確認: 似た Issue なし（--dry-run 済み）
```

## 4. 立てる（人間が OK したら）
```bash
npm run issue -- <種類> <宛先id> "<題名>" --body-file <下書きのパス> [--label area:front] [--label screen:home] [--blocked-by <先に終わるべき Issue の番号>]
```
- ラベル（`--label`）は、種類のほかに付ける目印。`area:front|back|native|contract|test`（どこを触るか）、`screen:<画面id>`（どの画面か）、`demo:D<番号>`（台本のどこか）を使う。無いラベルは自動で作る。
- 依存（`--blocked-by`）は、**この新しい Issue が先に終わるべき Issue**。本文に `Depends on #番号` が入り、GitHub 標準の依存関係（Blocked by）にも登録される。標準の登録に失敗しても Issue は作られ、本文の記載は残る。
- ブロッカー（今の Issue が新しい Issue に依存する）の場合は、今の Issue 側の本文に依存を足す必要がある。`gh issue edit` は使わず、今の Issue へのコメントで人間に知らせる。
- 本文のファイルは、リポジトリの外（スクラッチ領域）に置く。結果の URL を控える。
- 立てたら、**今の Issue にコメント**で知らせる（先頭に `<自分のid>:`）: 「…は #<新> に切り出した。この Issue では扱わない」。
- ブロッカーの場合は、作業を止めて人間に報告する（待つ間は別のステップへ）。

## 5. 今の Issue に戻る
- 切り出した内容は、今の Issue のコードにもテストにも入れない。
- 今の Issue を完了したら、セッション終了前のチェック（one-issue-one-session）で「切り出した Issue の一覧」を報告する。

## やらないこと
- 人間の確認なしに Issue を立てる。
- `--force` で重複確認を回避する（別件だと確かめた場合のみ）。
- 1 つの Issue に複数の話題をまとめる。
- GitHub Project への登録は、人間の確認を取ってから別途行う。
