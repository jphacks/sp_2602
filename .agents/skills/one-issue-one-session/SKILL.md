# 1 Issue = 1 Session プロトコル

## 0. セッション開始時の手順（作業に入る前）
1. 同じリポジトリで動く他のセッションがいないか確認する（`ListAgents` が使えるなら使う）。いたら人間に知らせる。
2. **最新のコードを取り込む。** 作業ブランチにいるなら `git pull --ff-only`。これから着手するなら、最新の `main` からブランチを切る（`npm run step -- S<番号> <英語名>`。ステップ表にない作業は `--adhoc`）。`--ff-only` で進めない（履歴が分かれている）ときは、勝手にマージせず人間に報告する。
3. 今回の担当 Issue（#X）を `gh issue view <番号>` で読み、**完了条件**（テスト条件を含む）を確かめる。1 セッションで終わる大きさ（30 分程度）か確認し、大きければ作業前に人間へ報告して分ける（`plan-issues` / `spawn-issue`）。
4. 前のセッションの会話には頼らない。必要な前情報は Issue 番号とソースコードから読む。

## 概要
本SKILLは、GitHub Issuesと連動した「1 Issue = 1 Session」開発体制において、AIエージェントが厳格に遵守すべき動作ルールおよびプロトコルを定義したものです。

---

## 1. 基本行動原則
1. **担当Scopeの遵守**:
   - あなたのタスクは指定された**1つのGitHub Issue（#X）の実装およびテストのみ**です。
   - コンテキスト汚染およびトークン消費を抑えるため、他Issueの領域や無関係なリファクタリングを勝手に行わないでください。
2. **スコープ膨張の禁止（例外処理の別Issue化）**:
   - 実装中に未考慮の境界条件、例外処理、あるいは追加機能のアイディア（「0のときの挙動」「別ログイン方式」等）を発見した場合、現在の作業コードに含めてはいけません。
   - 発見した例外事項は「別Issue候補（差し込みタスク）」として人間に報告し、メインIssueの実装をシンプルに完了させてください。

---

## 2. 開発・品質管理プロトコル
1. **テスト同梱基準の遵守**:
   - Issue内に定義されたテスト基準（単体テスト・動作検証手順）を満たすコードとテストコードをセットで出力してください。
2. **Linterおよび静的解析への適合**:
   - リポジトリで設定されているLinterおよびCI/CDチェック（構文エラー、フォーマット違反）に100%適合するコードを作成してください。

---

## 3. セッション終了・確認プロトコル（Closing Check）
人間（開発者）から以下のフレーズで問われた場合、必ずセッション終了前チェックを実行してください。

> **質問フレーズ**: 「このセッションを閉じて失われる情報はありませんか？」

### 必須自己診断チェック項目:
1. **未コミットファイルの有無**:
   - 作成・修正したコードやドキュメントで、コミット漏れになっているファイルはないか。
2. **チャット内合意事項の反映漏れ**:
   - セッション中のやり取りで決定した仕様変更や補足指定（例: 「UIカラーの調整」「ドキュメント記述」等）が、ファイルに正しく書き込まれているか。
3. **新規Issue切り出しの確認**:
   - 本セッション中に発覚した例外パターンや後回しにすべき事項が、報告漏れになっていないか。

チェック結果に問題がなければ、「失われる情報はありません。コミットおよびIssueのクローズが可能です。」と回答してください。

## 3.5 完了処理（チェックに問題がなかったあと）
グローバルの運用ルールで、**セッション完了時のプッシュは個別の依頼がなくても実行してよい**と事前に許可されている。次の順に進める。

1. **完了条件を確かめる。** Issue の完了条件を 1 つずつ満たしたことを示す（テスト・確認コマンドの結果の要点）。`npm run check` が通っていること。満たせていなければ、コミット・クローズに進まず、理由を報告する。
2. **コミットする。** 他のセッションの変更を巻き込まないため、`git status` と、ステージするファイルごとの `git diff -- <file>` を読み、**個別のファイル名で** `git add` する（`git add -A` / `git add .` は禁止）。身に覚えのない変更が混ざるファイルは、ステージせず人間に報告する。コミット直前にブランチと HEAD が動いていないことも確かめる。メッセージは Conventional Commits で、本文に「なぜ」を書く。
3. **プッシュする。** `git push`（初回は `git push -u origin <ブランチ>`）。`main` / `master` への force push はしない。`--no-verify` は使わない。
4. **Issue をクローズする。** `gh issue close <番号> --comment "<自分のid>: <やったことの要点>"`。このリポジトリは PR → `npm run merge` の運用なので、PR を作る運用の Issue は、PR 本文に `Closes #<番号>` を入れておけばマージ時に閉じる。**PR の作成は、人間の明示的な依頼があるときだけ**行う。
5. **報告する。** 切り出した別 Issue の一覧（`spawn-issue`）、コミットのハッシュ、プッシュ先、閉じた Issue 番号を伝えて、セッションを閉じてよいと知らせる。

この手順は、コミット・プッシュ・クローズが「できる」状態を作るためのもの。`pre-commit` や CI が失敗したら、バイパスせず原因を直す。同じ失敗が 2 回続いたら止めて報告する。

---

## 4. このリポジトリでの運用メモ
- 別 Issue 候補は、今の Issue に混ぜずにスキル `spawn-issue` の手順で下書きにし、人間の確認を取ってから `npm run issue` で立てる（AGENTS.md「絶対に守ること」）。
- 検査は `npm run check`、マージは `npm run merge`。詳細は AGENTS.md を見る。
