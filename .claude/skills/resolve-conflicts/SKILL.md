# コンフリクト解決プロトコル

方針: **AI は案を作り、検証し、理由を見せる。片方を捨てる判断は人間が行う。**

## 0. 始める前に
- `git branch --show-current && git log --oneline -1` で、ブランチと HEAD を控える（途中で動いていたら止めて報告）。
- 同じリポジトリで動く他のセッションがいないか確認する（`ListAgents` が使えるなら使う）。いたら人間に知らせる。
- 取り込みは **`git merge`** で行う。`git rebase` は履歴を書き換えるため、人間の確認なしにはしない。
- 競合を捨てる形の解決（`git checkout --ours/--theirs` での一括採用、`git merge --abort` 以外の巻き戻し）は、人間の確認なしにしない。

## 1. 双方の意図を集める（読むだけ。何も壊さない）
```bash
git status                       # 競合しているファイルの一覧
git log --merge --oneline -- <file>   # 競合に関わる両側のコミット
git log --merge -p -- <file>          # 両側の差分と本文（「なぜ」）
```
- 各コミット本文、PR の本文（`gh pr view <番号>`）、関連 Issue、`docs/members/<id>.md`（担当範囲）を読む。
- 意図が本文から読み取れなければ「推測」と明記する。推測で片方を捨てない。

## 2. 競合を種類で分ける
| 種類 | 例 | 対応 |
|---|---|---|
| A. 両方を残せる | 同じ場所に別々の行を足した／import や export の追加が重なった／別々の関数の追加 | AI が両方を残して自動で解決する |
| B. 片方を捨てる必要がある | 同じ値を別の値に変えた／同じ関数を別方針で書き換えた | **解決しない。** 双方の意図・案・おすすめを示して人間に聞く |
| C. `contracts/` の競合 | schemas.ts / api.ts / screens.md / tokens.ts / CHANGELOG.md | **人間に聞く。** 変更記録は docs/rules/changes.md の手順に従い、`contracts/CHANGELOG.md` は両側の行を残す |
| D. 他人の担当部分 | `docs/members/` で他の人の担当になっているファイル | その担当者に聞いてから解決する（docs/rules/git.md） |
| E. 生成物・ロックファイル | package-lock.json など | 手で直さず、元の設定から再生成する。再生成の方法に迷ったら人間に聞く |

迷ったら B として扱う。

## 3. 解決する（A のみ）
- 競合マーカー（`<<<<<<<` `=======` `>>>>>>>`）が残っていないことを確認する: `git grep -nE '^(<<<<<<<|=======|>>>>>>>)'`
- 対象ファイルだけを個別に `git add <file>` する（`git add -A` / `git add .` は禁止）。
- B・C・D が残っている間は、コミットしない。人間の返事を待つ。

## 4. 検証する（取りこぼしを減らす）
1. `npm run check` を実行し、全文の結果を確認する。**通すためにテストを消す・skip する・期待値を変えることはしない。**
2. **両側の変更が残っているか比べる。** 解決後の状態を、双方の親と比べる:
   ```bash
   git diff HEAD            # 自分の側と比べて、取り込んだ内容が入っているか
   git diff MERGE_HEAD      # 相手の側と比べて、自分の内容が残っているか
   git diff --cc            # 競合した部分だけの、両親との結合差分
   ```
   両側のコミットが追加した行・関数・型が、意図なく消えていないかを確認する。
3. `contracts/` に触れた場合は、`contracts/CHANGELOG.md` に変更の記録が残っているか確認する。
4. 検証で失敗したら、原因を直して再検証する。**同じ不具合の修正に 2 回失敗したら止めて人間に報告する。**

## 5. 報告する
ファイルごとに短く、次の形で報告する。

```
ファイル: <path>
種類: A / B / C / D / E
双方の意図: 自分側「…（コミット …）」 / 相手側「…（コミット …）」
解決: <両方を残した／人間に確認待ち>
理由: <なぜそうしたか>
推測の有無: <推測した点／なし>
検証: npm run check → <結果の要点> ／ 両側の変更が残っているか → <確認結果>
```
- 確認待ち（B・C・D）がある場合は、最初にそれを書く。
- コミットは、全ての競合の解決と検証が済み、人間が確認した後に行う。メッセージは「なぜ」を本文に書く。

## 6. このリポジトリでの運用メモ
- 競合を起こしにくくする: 1 ステップ = 1 PR で小さく出し、着手前に最新の main からブランチを切る（AGENTS.md）。
- マージは `npm run merge`（CI が通るまで待つ）。`gh pr merge` は直接使わない。
- 他人の担当部分を直したくなったら、`npm run issue -- bug <担当者id> "題名"` で頼む。
