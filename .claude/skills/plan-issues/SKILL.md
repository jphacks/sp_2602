# 要件・設計から Issue を一括で立てる

方針: **先に計画（表）を作り、人間が承認してから、まとめて立てる。** 勝手に立てない。計画の段階で「拾い漏れ」「大きすぎ」「依存の循環」「テストが書けない」を機械的に潰す。

## 0. 始める前に
- `gh repo view` で GitHub のリモートがあることを確認する。なければ人間に聞く（勝手に作らない）。
- `npm run now` で自分の id と状況を確認する。
- 既に open な Issue があれば先に一覧する（`gh issue list --state open --limit 200`）。重複して立てない。

## 1. 元の資料を読む（信頼の高い順）
1. `docs/DEMO.md`（最上位の仕様。D番号の台本。Stretch は対象外）
2. `docs/requirements/decisions.md`（決まったこと）と `open.md`（未決のこと）
3. `contracts/`（`schemas.ts` / `api.ts` / `screens.md` / `native.ts`）
4. `docs/flow/`、`docs/design/`（画面の流れ・設計）
5. `docs/members/*.md`（担当の場所・触らないファイル）、`docs/rules/team.md`（役割分担）

資料どうしが食い違うときは、上の順に正とし、食い違いを人間に報告する。**資料に無いものは Issue にしない。** 推測で補った項目は「推測」と明記する。

### 1.5 図をテキストにする（図が Figma / FigJam にしかないとき）
- 画面の流れ・データの流れが `docs/flow/` などに**テキスト（Mermaid 記法など）で無い**場合、AI は Figma / FigJam の図を直接読めないので、そのまま分解しない。
- 人間から図の内容（画面名・遷移・操作・データの流れ）を聞き取るか、スクリーンショットを見て、**Mermaid の下書きを `tmp/flow-draft/` に作る**。画面遷移は `flowchart`、状態は `stateDiagram-v2`、データの流れは `flowchart` で書く。
- 下書きを人間に見せ、図と合っているか確認してもらう。**`docs/flow/` は人間確認領域なので、AI は勝手に書き込まない。** 置いてよいと言われたら、そこに置く（担当は `docs/rules/team.md` の front-b）。
- 確認された Mermaid を、手順 2 の分解の入力にする。図が無いまま推測で Issue を作らない。

## 2. 動作の単位に分解する
- 次の観点を漏れなく見て、**1 つの動作を確かめられる単位**に分ける。「〜周り全般」「〜の整備」のような大枠にしない。
  - DEMO.md の D番号ごとの画面と操作
  - `screens.md` の画面一覧と遷移
  - `api.ts` の API（1 つ = 入力の検査・処理・エラーなど動作ごと）
  - `native.ts` の Kotlin の窓口（使用時間の取得、制限画面など）
  - 横断: エラー表示、`MOCK=1` で動くこと、デモ用の固定入力（`fixtures.ts`）
- **未決（`open.md`）に依存するものは Issue にしない。** 計画の末尾に「保留」として、何が決まれば立てられるかを書く。
- 契約の追加・変更が必要なものは `change-request`（宛先は lead）。実装 Issue は契約を足す Issue に依存させる。

## 3. 粒度を揃える（30 分程度）
- 1 Issue = 1 動作 = 1 担当 = 1 PR = **30 分程度**。超えそうなら分ける。短すぎて他と同時にしか確かめられないものは、まとめる。
- ステップ表（`docs/members/*.md` の S番号、30〜60 分）がある場合、1 ステップに Issue が複数入ってよい。ステップに対応するときは本文の「参考」に `S<番号>` を書く。
- 全体で **20〜60 件**を目安にする。大きく外れたら、粒度を見直してから人間に報告する。

## 4. 担当・依存・テストを決める
- **宛先（対応する人）:** `docs/members/` の「担当の場所」で決める。決められなければ空にせず、人間に聞く。
- **種類:** 通常は `task`。バグは `bug`、契約は `change-request`、待ちは `blocked`。
- **依存:** 画面は **契約**に依存させる（実装されたサーバではなく）。`MOCK=1` で並行して作れるため。
  - 依存は ID で書く（`P3` は `P1` と `P2` に依存）。**循環がないこと**を確かめ、立てる順（依存される側が先）に並べる。
  - 依存が長く連なるところ（最長の鎖）を示し、先に着手すべきものを指摘する。
- **完了条件にテストを必ず入れる:** 単体テスト、または確かめる手順（コマンドと期待する結果）。テストが書けないものは、動作の単位として曖昧なので、分け直すか Issue にしない。

## 5. 計画を書く（まだ GitHub には何もしない）
`tmp/issue-plan.md`（リポジトリ内の `tmp/` は Git 管理外）に表で書く。

| ID | 題名 | 種類 | 宛先 | ラベル | 根拠（ファイル・節） | 依存 | 完了条件・テスト | 参考 |
|---|---|---|---|---|---|---|---|---|
| P1 | [D2] 入力フォームを表示する | task | front-b | area:front, screen:home, demo:D2 | DEMO.md D2 / screens.md home | — | `npm run shot` で `home` に入力欄が出る | S2 |

ラベルは、機能と画面ごとに付ける（進み具合を絞り込んで見るため）。`area:front|back|native|contract|test`（どこを触るか）、`screen:<画面id>`、`demo:D<番号>`。全 Issue に `area:` を 1 つは付ける。

題名は 1 動作を「〜する」で書き、台本に対応するなら `[D番号]` を頭に付ける。各 Issue の本文は spawn-issue のひな型（概要・発見の経緯→「根拠」・完了条件・参考）で書く。

## 6. 計画を自己点検する（人間に見せる前に）
- [ ] **拾い漏れ:** DEMO.md の全 D番号、`screens.md` の全画面、`api.ts` の全 API、`native.ts` の全窓口に、対応する Issue が 1 つ以上ある
- [ ] **根拠:** 全 Issue が資料のどこから来たか示せる（資料に無いものが混ざっていない）
- [ ] **粒度:** 30 分を大きく超えるものがない
- [ ] **依存:** 循環がない。依存先が計画内に存在する
- [ ] **テスト:** 全 Issue に完了条件のテスト（または確認手順）がある
- [ ] **担当:** 全 Issue に宛先がある。同じ人に偏っていないか（件数を集計して示す）
- [ ] **重複:** open な既存 Issue と題名が似たものがない（手順 7 の `--dry-run` でも確かめる）

## 7. 人間に見せて、承認を得る
- 件数、担当別の件数、依存の最長の鎖、保留（未決に依存）の一覧、資料どうしの食い違いを、先に短く報告する。
- 計画ファイルのパスを示し、直してほしい点を聞く。**承認が出るまで GitHub には何も書かない。**
- 承認後、重複確認だけを全件に対して先に行う:
  ```bash
  npm run issue -- <種類> <宛先> "<題名>" --dry-run
  ```
  似た Issue があるものは立てずに人間へ報告する（別件なら人間が `--force` を許可する）。

## 8. まとめて立てる（承認後）
- **依存される側から順に**、1 件ずつ立てる:
  ```bash
  npm run issue -- <種類> <宛先> "<題名>" --body-file <本文のパス> --label area:front --label screen:home --blocked-by <先に終わる Issue の番号>
  ```
  本文のファイルは `tmp/issue-bodies/` に作る。引数で渡さない。ラベルは無ければ自動で作られる。
- 立てるたびに、`P番号 → #Issue番号` の対応を `tmp/issue-plan.created.json` に追記する。後続の Issue の `--blocked-by` には、この対応から依存先の番号を渡す（本文に `Depends on #番号` が入り、GitHub 標準の依存関係にも登録される）。標準の登録に失敗しても Issue は作られるので、警告が出たら報告する。
- **途中で失敗したら止める。** 作れた分と作れなかった分を報告する。再開するときは、対応表にあるものを飛ばす（二重に立てない）。
- 終わったら、全件の `P番号 / #番号 / 題名 / 宛先 / 依存` の一覧を報告する。

## 9. 終わったあと
- GitHub Project（カンバン）への登録は、人間の確認を取ってから別途行う。
- 立てた Issue は、作業中に見つけた追加を混ぜない（`spawn-issue` で別 Issue にする）。1 Issue = 1 セッションで進める（`one-issue-one-session`）。
- 資料（DEMO.md や契約）が変わったら、計画を作り直さず、差分の Issue だけを追加・整理する。

## やらないこと
- 承認前に GitHub に書く。
- 資料に無い機能を足す、Stretch を入れる、未決のものを推測で立てる。
- `--force` で重複確認を回避する。
- 1 つの Issue に複数の動作を詰める。
