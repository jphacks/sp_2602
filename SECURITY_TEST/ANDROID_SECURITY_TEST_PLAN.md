# Slope Android / API セキュリティテスト計画

更新日: 2026-10-18  
目的: ローカルで起動したSlopeと専用Androidエミュレーターを対象に、既知のモバイルアプリ/API事故で見られた攻撃パターンを安全に再現し、結果を記録する。

## 1. 対象と現在確認できている範囲

### 対象

- このリポジトリ内のSlopeバックエンドと、後日接続するAndroidアプリ。
- 接続先はローカル開発サーバーのみ。テスト用親A・子A・親B・子Bのデータを使う。
- アプリの通信観察は専用エミュレーター上で行う。実ユーザーのデータや実サービスを使わない。

### 2026-10-18時点の実装状況

- この計画は `main` の `9883d2b` を基点にしたセキュリティ作業ブランチで確認する。
- Androidアプリのソースは `src/app` と `modules/kit-native/android` にある。リリースAPKを使った動的検査はまだ実施していない。
- `backend/src/server.ts` はDB接続付きの `GET /health` と、それ以外への404応答を提供する。アプリAPIは `src/server/route.ts` と `src/server/handlers/` に実装されている。
- 認証、親子連携、利用実績、設定などのAPI実装は存在するが、この計画に沿った認証・認可・漏えい検査の結果はまだ確認していない。
- 専用Androidエミュレーターでの動的検査と、各APIのセキュリティ検査は未実施。実装があることだけで安全性確認済みとは扱わない。

## 2. 事故事例から採用する観点

| 事例 | 公開報道で確認された問題 | Slopeで検査する観点 |
|---|---|---|
| Twilio Authy（2024） | 未認証APIエンドポイントからアカウント関連情報が識別された。 | 認証なしの応答、ユーザーID列挙、応答差によるアカウント有無の推測、過剰な応答項目 |
| Teaアプリ（2025） | 旧ストレージにあった本人確認画像等が不正アクセスされた。 | テスト用個人データの公開範囲、ストレージ権限、不要データ保持、URLを知るだけでの取得可否 |
| Mobile Guardian（2024） | 管理プラットフォーム侵害後に端末データ消去が発生した。 | 高権限操作の認可、影響範囲、確認ゲート、監査記録、誤操作時の復旧性。Slopeに遠隔消去機能があるとの意味ではない。 |

この計画は事故の手口を第三者環境で再現するものではなく、報道された失敗の原因クラスをSlopeのローカル環境で検査するもの。OWASP MASVS/MASTGの認証・通信・保存・プラットフォーム・プライバシー分類を土台にする。

## 2.1 重点テーマ: アカウント／個人情報の漏えい防止

今回のセキュリティ確認では、個人情報の漏えい防止を最優先にする。SlopeのMVP仕様と現行DBスキーマから、少なくとも次の情報を保護対象として扱う。実際の認証方式や保存項目は実装が揃った段階で再確認する。

| データ | 例 | 重要度と扱い |
|---|---|---|
| 認証秘密 | Bearer token、OAuth callback情報、セッション | **最高**。ログ・URL・スクリーンショット・バックアップへ出さない。ログアウト／期限切れで失効を確認。 |
| 親子関係 | 親ID、子ID、role、family link | **高**。IDだけを知っても閲覧できないよう全APIで認可。応答・ログで不要な他者IDを返さない。 |
| 子供の利用履歴 | 日付、アプリID、利用分数 | **高**。行動傾向が分かるデータとして保護し、子供本人と紐づく親だけに最小範囲で返す。 |
| QR連携情報 | 一時トークン、期限、使用状態 | **最高**。QR画面・ログ・履歴・通知から再利用可能な値を漏らさず、短命・一回限りをサーバー検証。 |
| 設定・計画 | 日別上限、テスト期間、対象外アプリ | **中〜高**。本人・認可された親子以外に開示しない。変更者とversionをサーバー側で検証。 |
| 表示名などのプロフィール | `displayName` 等 | **中**。必要な画面に限って返し、他のデータと結合した一覧を不用意に作らない。 |

### 漏えい経路ごとの確認手順

| ID | 漏えい経路／ローカルでの確認 | 合格条件 |
|---|---|---|
| PII-01 | 親A・子A・親B・子Bに、識別用の架空プロフィールと異なる利用記録を登録。未認証、別家庭、同じ家庭の別roleで各APIを読み、応答JSON全体を比較する。 | 所有者と役割に必要な情報だけを返し、別家庭のID・プロフィール・履歴は一切含まない。 |
| PII-02 | 親Aの正規リクエストから子ID、日付、submission IDをテスト用の別家庭IDに差し替え、一覧・詳細・集計を個別に1回ずつ要求する。 | endpointごとに認可し、IDを推測／取得できても別家庭の行は返らない。集計値からも他家庭の情報を推定できない。 |
| PII-03 | 正常な応答に不要な列（内部UUID、role、作成者、認証状態、全family link等）が含まれないかJSONとアプリ画面で確認する。 | 画面に必要な項目のみ返す。内部IDは必要な処理に限り使い、他人のID一覧を返さない。 |
| PII-04 | Logcat、サーバーの開発ログ、クラッシュログ、分析イベントを、ログイン・QR表示・利用記録同期の前後で確認する。 | token、QR秘密、氏名等、詳細な利用履歴が記録されない。調査用相関IDは秘密と切り離される。 |
| PII-05 | APK内の保存領域・SharedPreferences・SQLite・キャッシュ・バックアップ対象をテストAVD内で確認し、ログアウト前後とアカウント切替後を比較する。 | 認証秘密はOS保護された保存方式を使う。ログアウト後／別ユーザー切替後に前利用者の保護データが残って表示されない。 |
| PII-06 | URL、deep link、通知、クリップボード、共有Intent、最近使ったアプリ画面にtoken、QR内容、履歴が現れないか確認する。 | 再利用可能な秘密や不要な利用詳細を露出しない。QRを画像として保存しても期限・一回制限がサーバー側で効く。 |
| PII-07 | エラー条件（無効ID、認可拒否、DB停止、期限切れtoken）をそれぞれ1回起こし、画面・HTTP応答・ログを確認する。 | SQL、stack trace、環境変数、別ユーザー情報、tokenの一部を応答しない。エラー文からアカウント有無を推測しにくい。 |
| PII-08 | 同じ架空の表示名・利用時間パターンを複数ユーザーに設定し、画面／集計APIが不要に複数人のデータを混ぜないか調べる。 | 個人単位の情報を集約・共有する場合も認可境界と集計単位が明示され、他ユーザーの履歴が混入しない。 |
| PII-09 | QR発行後、期限切れ、使用済み、ログアウト、再発行の各状態で、QR画面・履歴・ログ・古いリンクを確認する。 | QR秘密を再取得・再利用できず、再発行時に古い未使用tokenも仕様どおり無効化される。 |
| PII-10 | ローカルDBにテスト記録を作成し、利用記録削除／連携解除／アカウント削除機能がある場合、各操作後にAPI、DB、端末cache、送信待ちqueueで残存を確認する。 | 削除範囲と保持期間が仕様どおりで、削除済みデータが同期再送や別画面から復活しない。機能未実装なら `BLOCKED`。 |

### 個人情報の合格ゲート

- どのデータを誰に返すかを、各APIでサーバー側認可として実装・検証する。UIの非表示だけでは合格にしない。
- テスト証跡には架空アカウントと合成データを使い、token・QR・個人情報そのものを添付しない。
- 個人情報を含む操作の期待応答は、HTTP statusだけでなく、レスポンスJSON・DB変化・端末cache・ログをまとめて確認する。
- 未実装API・Android APKがない機能は `BLOCKED` とし、仕様上の期待だけでPASSにしない。

### 予防策の実装要件（バックエンド／Androidフロントエンド）

#### バックエンド: 認可とデータ露出をサーバー側で止める

| 優先度 | 実装要件 | 合格条件 |
|---|---|---|
| **P0** | Google等のログイン結果をサーバーで検証し、署名・issuer・audience・有効期限を確認してから内部ユーザーへ紐づける。クライアントが送る `role` や `userId` を本人確認に使わない。 | tokenの改変・別audience・期限切れを拒否し、roleはサーバー側のDB情報から決定する。 |
| **P0** | 認証主体を各リクエストの実行コンテキストに設定し、すべての家族データクエリを `authenticated user + verified family link + allowed role` でスコープする。 | 親Aの主体で子BのIDを指定しても、read/write両方が拒否される。UI上の制御だけに依存しない。 |
| **P0** | DBモデルをそのまま返さず、endpointごとの許可項目だけを持つresponse DTOを定義する。プロフィール・利用履歴・内部IDを一括返却しない。 | API応答に当該画面に不要なtoken、他家庭のID、内部列、不要な個人属性が含まれない。 |
| **P0** | QR用秘密値は暗号学的乱数で生成し、DBには可能ならハッシュを保存。短い有効期限、原則一回限り、使用確定と親子link作成を同一トランザクションで行う。 | 平文tokenのDB・ログ露出がなく、期限切れ・再利用・競合リクエストで二重連携しない。 |
| **P0** | Bearer token、OAuth code、QR token、個人情報をURL・例外・アクセスログ・分析イベントへ出さない。ログは許可項目のallowlist方式で構成する。 | 失敗時を含むserver/client logsに秘密値や詳細な利用履歴がない。 |
| **P1** | 入力をendpointごとに厳格なschemaで検証し、Drizzle等のparameterized queryを使う。クライアント検証は補助とみなす。 | 型・長さ・範囲・日付をサーバーでも検証し、未知項目やmass assignmentでrole/ownerを変更できない。 |
| **P1** | ログイン、QR発行、検索、同期に控えめなレート制限を設ける。エラー応答を均一化し、ID列挙やアカウント有無の判定を難しくする。 | 小規模な反復で429等の制御が働き、アカウント存在の有無を応答差で判定しにくい。 |
| **P1** | DB接続はTLS、DBユーザーは必要最小権限、backup・retention・削除方針を定義。秘密情報は環境変数／secret管理へ置き、APKやGitへ入れない。 | backupを含めアクセス権と保持期間を説明でき、開発／テスト／本番の資格情報を分離する。 |

#### Androidフロントエンド: 端末上のコピー・漏えい・偽装を減らす

| 優先度 | 実装要件 | 合格条件 |
|---|---|---|
| **P0** | 認証tokenはAndroid Keystoreを使う保護された保存方式で扱い、平文SharedPreferences、Logcat、URL、Intent extra、clipboardへ置かない。 | エミュレーター内の通常のアプリファイル・ログ・最近使った画面からtokenを取得できず、ログアウト時に破棄される。 |
| **P0** | 画面・API clientでユーザー切替時にプロフィール、履歴、設定、未送信queueをユーザー単位で分離。ログアウト後は保護画面を再認証まで閉じる。 | 親Aログアウト後に親BでログインしてもAのcacheや送信待ちが表示・送信されない。 |
| **P0** | UIは必要なデータだけ取得し、子供向け画面では仕様にない生利用分数等を不用意に表示しない。親向け表示も認可済み対象のみに限定。 | 画面・通知・スクリーンショットプレビューに他者の履歴が混ざらず、最小限の情報だけを表示する。 |
| **P1** | API接続先はreleaseでHTTPSを必須にし、デバッグ用HTTP／プロキシ信頼設定をreleaseへ混ぜない。端末で証明書検証を無効化しない。 | release設定で不正証明書・平文接続が拒否され、debug例外はdebug buildだけに限定される。 |
| **P1** | AndroidManifestのexported component、deep link、共有Intentを最小限にする。外部Intentは入力として検証し、権限確認をサーバーでも行う。 | IntentやURIを直接開くだけでログイン、role変更、QR連携、家族データ取得が成立しない。 |
| **P1** | 端末内DB/cache/backup対象を見直し、保存不要な履歴は保持しない。クラッシュ・分析SDKへ個人情報を送らない。通知はロック画面で機微な内容を隠す。 | 保存項目・保持期限・第三者SDKの送信先が説明可能で、機微情報を不用意にバックアップ／通知表示しない。 |

#### 実装の進め方とリリース判定

1. **P0から着手:** データ項目と利用目的の一覧化 → tokenのサーバー検証 → 全APIの所有者認可 → response DTO最小化 → Androidの安全なtoken/cache管理。
2. **次に漏えい経路を閉じる:** ログ／通知／backup／Intent／通信設定を点検し、QR一回性・期限・競合処理をサーバーで実装する。
3. **その後に濫用耐性:** schema検証、レート制限、依存ライブラリ棚卸し、削除・保持・backup復元を整える。
4. 各P0要件について、正規アクセス成功と越権アクセス拒否の両方を自動/API検証し、Androidでは専用AVDでユーザー切替・ログアウト後の残存を確認する。
5. **リリースゲート:** P0の漏えい・越権ケースに未解決FAILがあればリリースしない。未実装や未検査はPASSにせずBLOCKEDとして残す。

## 3. 実施前の安全条件

1. Android Studioの専用AVD（例: `SlopeVerify`）とローカル開発サーバーだけを使う。
2. テスト用アカウント・架空データを作成し、実データをインポートしない。
3. エミュレーターのAPI接続先が `localhost` 相当のローカル転送先であることを確認する。Preview/ProductionのURL、実ユーザー用OAuth、実DB資格情報が入っていたらテストを始めない。
4. 通信プロキシを使う場合は、エミュレーターとローカルテスト通信だけに限定し、テスト後にCA証明書を削除する。
5. 負荷検査はローカル限定で、通常は1リクエスト/秒以下・各ケース20回以下にする。大量列挙、総当たり、実ユーザーID探索、DoS、遠隔消去、実データ削除は行わない。
6. 破壊的な操作の確認は、コード上の権限・確認UI・監査ログ・テスト用の取り消し可能な状態遷移で評価する。実端末初期化や本番相当データ消去を試さない。

## 4. 共通の記録方法

各項目に次を記録する。

- ケースID、日時、アプリのバージョン／APK SHA-256、Android APIレベル、サーバー起動コマンドとローカルURL。
- テストアカウントの役割（秘密情報は記録しない）、再現手順、期待結果、実結果、HTTPステータス、サーバーログ上の相関ID。
- 画面・通信ログの証拠は個人情報・Bearer token・Cookieを伏せる。
- 判定は `PASS`（期待どおり拒否／保護）、`FAIL`（越権・漏えい・クラッシュ等を再現）、`BLOCKED`（機能未実装等で未検査）で統一する。

## 5. テストケース一覧

### A. 認証・認可・API列挙

テストデータ: 親A↔子A、親B↔子Bの2組。IDを他人のデータへ差し替える場合も、自分が作ったテストIDだけを使う。

| ID | 攻撃パターン／手順 | 期待結果 |
|---|---|---|
| API-01 | Bearer tokenを付けず、保護対象APIを直接開く。 | 401相当で拒否。個人データや内部情報を返さない。 |
| API-02 | 空、壊れた形式、期限切れ、署名不正のテスト用tokenを送る。 | 認証拒否。例外スタックやtoken内容を応答に含めない。 |
| API-03 | 子Aのtokenで親向け設定変更APIを呼ぶ。 | 403相当で拒否し、設定が変化しない。 |
| API-04 | 親Aから、子Bの利用記録・設定を読むリクエストを試す。 | 対象ごとにサーバー側で親子関係を検査し拒否する。 |
| API-05 | 親Aの画面で子IDを子BのIDへ置き換えて読む／書く。 | 画面の非表示だけに頼らずAPIが拒否する。 |
| API-06 | 子Aが自分の利用記録を送る際、body内の `childId` を子Bに差し替える。 | token主体と対象子IDの不一致を拒否。 |
| API-07 | リクエストbodyの `role` / `createdByUserId` / `parentId` を親権限へ書き換える。 | クライアント指定の役割を信頼せず、認可拒否または無視する。 |
| API-08 | `backend/src/server.ts` の `GET /health` と未知のパス、および `src/server/route.ts` の各APIへ未認証でアクセスし、返却情報を確認する。 | health応答に秘密情報・環境変数・SQL詳細がなく、未知のパスは404。アプリAPIは認証境界を通し、未認証要求を拒否する。 |
| API-09 | 同じテスト用QRを期限前に2回読ませ、次に期限切れQRを送る。 | 成功は最大1回。期限切れ／使用済みは明確に拒否し、別の親子を結びつけない。未実装ならBLOCKED。 |
| API-10 | QRを発行した子Aとは異なる子IDをリクエストに指定する。 | QRトークンに紐づく子本人以外へ連携しない。 |
| API-11 | 連携APIのレスポンスを捨てて、同じリクエストを一度再送する。 | 冪等性を保ち、二重リンクや二重レコードを作らない。 |
| API-12 | 無効なIDと有効だが権限のないIDで応答本文・時間・サイズを比較する。 | アカウントや家族関係の有無を過度に推測できる差を作らない。 |

### B. 入力検証・業務ルール・DB境界

以下は専用ローカルAPIでのみ使う無害なテスト値。削除・更新ケースは作成したテスト行だけを対象にする。

| ID | 攻撃パターン／手順 | 期待結果 |
|---|---|---|
| IN-01 | 名前欄へ `' OR '1'='1` や `";--` を入力する。 | SQLとして実行されず、文字列として扱うか入力エラーになる。 |
| IN-02 | 名前欄へ `<script>alert(1)</script>`、`<img src=x onerror=alert(1)>` を保存し一覧で表示する。 | スクリプトとして実行されず、テキストとして安全に表示される。 |
| IN-03 | 名前に空文字、空白のみ、最大長ちょうど、最大長+1、絵文字・結合文字を送る。 | DB制約・UIの長さ定義と一致した検証エラー。500や文字化けにならない。 |
| IN-04 | 日付に存在しない日付、形式違い、開始日>終了日、極端な過去／未来日を送る。 | 4xx相当で拒否し、TZ変換で別日へ化けない。 |
| IN-05 | `usedMinutes` / `limitMinutes` に負数、0、小数、巨大整数、文字列、null、配列を送る。 | 型と範囲を検証。負の利用時間や整数オーバーフローを保存しない。0分上限は仕様上有効値。 |
| IN-06 | `appId` に空白のみ、長さ上限+1、制御文字を含める。 | 空値・上限超過を拒否し、ログや画面を壊さない。 |
| IN-07 | 未知のJSON項目やネストした `role`, `isAdmin`, `ownerId` を追加する（mass assignment）。 | 許可項目だけを更新し、権限・所有者・計算版を書き換えない。 |
| IN-08 | 同じ `submissionId` と同じpayloadを再送し、その後同じIDで内容だけ変える。 | 同一payloadは二重計上せず、異なるpayloadのID再利用は競合として拒否する。 |
| IN-09 | `configVersion` と `dailyLimits` / `testPeriods` の版を意図的に混在させる。 | 不整合を拒否するか、一貫した版を返す。古い応答が新しいキャッシュを上書きしない。 |
| IN-10 | 0件期間、重複期間、同日開始終了、計画開始日=D=0、上限0分で計算を確認する。 | 決定済み業務ルールに従い、0除算・負値・未確定の過去値変更を起こさない。未承認ルールはBLOCKEDとして記録。 |
| IN-11 | 通常サイズを超えるリクエストbody（例: 64 KiB超）を1回送る。 | 明示的なサイズ制限で拒否し、プロセスやDBが不安定にならない。 |
| IN-12 | SQL/JSON特殊文字をサーバーログ出力項目へ入れる。 | ログ改行・偽装を防ぎ、token等の秘密値を記録しない。 |

## 6. IPA情報から追加した攻撃シナリオ

IPAのトップページは、個々の攻撃手順を列挙するページではなく、「情報セキュリティ10大脅威」「脆弱性対策情報」「安全なウェブサイトの作り方」等への入口。そこで、IPAの2026年版脅威一覧と脆弱性対策項目からSlopeの構成に関係するものを選び、以下のローカル検査シナリオへ展開した。脅威名はIPAの分類、手順とSlopeへの当てはめはこのテスト計画で作成した内容。

IPAの個人向け脅威には、サービスからの個人情報窃取、不正ログイン、フィッシング、不正アプリによる被害などが挙げられている。組織向けでは、サプライチェーン、脆弱性悪用、内部不正、DDoS等が挙げられている。Slopeでは主に認証・API・端末内データに翻訳して確認する。フィッシングやランサムウェアの実行、実際のDDoSは実施しない。

### IPA-01 未認証APIと個人情報の露出

**対応するIPA観点:** インターネット上のサービスからの個人情報窃取。

1. テスト用アカウントで通常画面を操作し、アプリが呼ぶAPIの一覧を記録する。
2. 専用ローカル環境に限り、認証ヘッダーを外して各GETを1回ずつ呼ぶ。
3. パス・クエリに自分で作ったテストIDを指定し、応答にプロフィール、子供の利用履歴、設定、QR情報が混じらないことを確認する。
4. ステータス、応答サイズ、エラー形式を記録する。既知ID／存在しないIDの比較はテスト用IDだけで行う。

**合格条件:** 未認証では保護データが一切返らず、エラーからIDの存在や権限情報を容易に推測できない。

### IPA-02 親子ロール越境・IDOR

**対応するIPA観点:** 不正ログイン、アクセス制御・認可制御の欠落。

1. 親A↔子A、親B↔子Bを作り、それぞれに異なる利用記録を1件だけ登録する。
2. 親Aの正常な読取リクエストをローカルプロキシで複製し、子IDだけを子Bへ置き換えて1回送る。
3. 子Aのリクエストでは、body上の `childId` と `role` も他のテスト値へ置き換えて送る。
4. 画面を介さずAPIへ直接送信し、サーバー応答と両家庭のデータ状態を確認する。

**合格条件:** 全APIでtoken主体と親子関係をサーバー側で検証し、拒否応答後も子Bのデータは取得・変更されない。画面上のボタン非表示だけでは合格にしない。

### IPA-03 ログイン・セッションの再利用

**対応するIPA観点:** インターネット上のサービスへの不正ログイン、セッション管理の不備。

1. テストユーザーでログインし、テスト環境の通信ログ上でtokenの保存場所と有効期限の扱いを確認する。tokenそのものは報告書へ貼らない。
2. ログアウト後、同じ画面から戻る操作とアプリ再起動を行う。
3. ログアウト前のリクエストを1回だけ再送する。
4. 期限切れ・署名不正のテストtokenも各1回送る。

**合格条件:** ログアウト済み／期限切れtokenは保護APIで拒否され、再ログインまで以前の情報を表示・更新できない。エラー応答にtokenや署名検証情報が含まれない。

### IPA-04 SQLインジェクション

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のSQLインジェクション。

1. 名前・検索文字列など、ローカルAPIがDB検索に使うテキスト欄へ `test' OR '1'='1` を送る。
2. 追加で `test');--` を1回だけ入力し、画面表示と応答を確認する。
3. テストデータ件数が増減していないこと、サーバーがSQLエラーを返していないことを確認する。

**合格条件:** 入力は値として扱われるか4xxで拒否され、他ユーザーのデータ返却・DB変更・SQL詳細の露出がない。時間差を使う自動抽出や大量payloadは実施しない。

### IPA-05 XSS・保存データの安全な表示

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のクロスサイト・スクリプティング。

1. テスト名等へ `<script>alert(1)</script>` と `<img src=x onerror=alert(1)>` を保存する。
2. 一覧、詳細、通知、WebView画面など、保存値が再表示される箇所を確認する。
3. 文字列として表示されたか、HTMLとして解釈されたかを記録する。

**合格条件:** JavaScript実行・画面遷移・外部通信が起きず、入力は安全にエスケープされる。SlopeにWebView等がなければ対象外として記録する。

### IPA-06 パストラバーサル（ファイル機能がある場合のみ）

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のパス名パラメータ未検査／ディレクトリ・トラバーサル。

1. エクスポート／インポート等のファイル名パラメータが存在する場合だけ実施する。
2. テスト用ファイル名に `../slope-test-marker`、`..%2F`、`%2e%2e%2f` を指定する。OS上の既存ファイル名は指定しない。
3. テスト用一時ディレクトリの外にファイルが生成・読取されないことを確認する。

**合格条件:** パスを正規化して許可ディレクトリ内に制限するか、入力を拒否する。ファイル機能がなければ `N/A`。

### IPA-07 コマンドインジェクション（外部プロセス呼出しがある場合のみ）

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のOSコマンド・インジェクション。

1. アプリ／バックエンドに外部プロセスを呼び出す機能があるか、ソースを確認する。該当コードがなければ `N/A`。
2. 該当するテキスト欄がある場合、`slope-test;marker` や `slope-test|marker` のような無害な文字列だけを1回送る。
3. プロセス実行やファイル作成を誘発するOSコマンド文字列は送らない。応答、ログ、テスト用領域に予期しない処理結果がないか確認する。

**合格条件:** 入力をシェルへ連結しない。用途があれば引数を安全に分離し、許可リストで制限する。

### IPA-08 HTTPヘッダーインジェクション

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のHTTPヘッダー・インジェクション。

1. リダイレクト先、表示名等がHTTPヘッダーに使われる機能がある場合だけ実施する。
2. 値に改行相当（`%0d%0a`）と `X-Slope-Test: marker` を含めたテスト値を1回送る。
3. ローカル応答のヘッダーを確認し、利用者入力で新しいヘッダーやレスポンス分割が生じないことを調べる。

**合格条件:** 改行を拒否／除去し、任意ヘッダーを注入できない。該当機能がなければ `N/A`。

### IPA-09 CSRF（Cookie認証のWeb画面/APIがある場合のみ）

**対応するIPA観点:** IPA「安全なウェブサイトの作り方」のCSRF。

1. Slopeにブラウザー／WebViewからCookieを自動送信する更新APIがあるか確認する。Bearer tokenを明示して送るAPIだけなら、原則このケースは対象外。
2. ローカル検証用の別オリジンページから、テストアカウントの設定を変更するリクエストを1回試す。
3. CookieのSameSite属性、CSRF token、Origin/Referer検査の有無を確認する。

**合格条件:** 別オリジンから認証済み状態を悪用した変更が成立しない。外部サイトを使わずローカル内で完結させる。

### IPA-10 不正アプリ／Intent経由の操作

**対応するIPA観点:** 不正アプリによるスマートフォン利用者への被害。

1. APKのManifestでexported Activity/Service/Receiver/Provider、URI scheme、必要権限を一覧化する。
2. エミュレーターから欠落値・型違いを含むIntent/deep linkを開き、ログイン・QR連携・設定画面を確認する。
3. テスト用の呼び出し元アプリまたはADBのIntent送信で、非公開画面・処理へ外部から到達できないか確認する。
4. 「QRを読んだ」だけで連携確定せず、認証済み利用者とサーバー側の検証が必要なことを確認する。

**合格条件:** 公開が必要な入口だけが外部から呼べ、外部Intentだけで認証・役割・親子関係を変更できない。マルウェアAPKの導入はしない。

### IPA-11 サプライチェーン／依存ライブラリ

**対応するIPA観点:** サプライチェーンや委託先を狙った攻撃、脆弱性悪用。

1. `backend/package-lock.json` とAndroidのGradle依存定義・ロックファイルを一覧化する。
2. 推移依存、古い／非推奨SDK、開発用パッケージがreleaseへ混入していないか確認する。
3. IPA/JVNの脆弱性情報で、実際に使う製品・バージョンに一致する注意情報だけ照合する。
4. lockfileの想定外差分や、配布APKに含まれる未承認SDK・固定秘密値を記録する。

**合格条件:** 採用理由と更新責任が追える。未知の依存を勝手に実行したり、ネット上の第三者ホストをスキャンしたりしない。

### IPA-12 入力ファジングとリソース消費

**対応するIPA観点:** IPAのファジング教材、脆弱性悪用、DDoS／サービス妨害。

1. JSON APIが実装された後、専用ローカルAPIに対し、必須項目欠落、型違い、境界値、未知項目、最大長+1のケースを少数ずつ送る。
2. 本計画の上限（1 req/s以下、各ケース20回以下）を守り、サイズ上限を超えるbodyは1回だけ確認する。
3. クラッシュ、5xx、遅延の持続、メモリ急増、重複保存、送信キューの暴走を観察する。

**合格条件:** 不正入力は安定して4xxで拒否され、ローカルサービスが通常状態へ戻る。並列大量送信、無限ループ、公開サーバーへの負荷試験は実施しない。

### IPA-13 内部不正・端末上の情報露出

**対応するIPA観点:** 内部不正による情報漏えい等、サービスからの個人情報窃取。

1. ログアウト前後のLogcat、最近使ったアプリ画面、通知、クリップボード、アプリバックアップ対象をテスト用アカウントで確認する。
2. 親Aの端末状態からログアウトし、親Bでログインして、親A／子Aのキャッシュが表示されないことを確認する。
3. ローカルDBの権限とバックアップ対象を確認する。データのコピーはテストAVD内に留める。

**合格条件:** token・QR秘密・利用履歴が不要な場所へ残らず、ユーザー切替後に別ユーザーのキャッシュを表示しない。

### IPA-14 フィッシング／偽ログイン導線

**対応するIPA観点:** フィッシングによる個人情報等の詐取、不正ログイン。

1. ログイン画面、外部ブラウザー遷移、OAuth callback、deep linkの許可scheme/hostをコードと実機で確認する。
2. 自分で作った無効host・似た文字列host・未知schemeのcallbackをエミュレーターから開く。
3. 認証tokenをURLクエリ、WebView JavaScript、クリップボードへ出す導線がないか確認する。

**合格条件:** 許可した認証先だけを使い、偽hostからログイン成功状態を作れず、tokenをURLへ含めない。実際の偽ログインサイト作成や第三者への送信はしない。

### IPA-15 バックアップ／復旧と破壊的操作

**対応するIPA観点:** ランサム攻撃による被害、内部不正、可用性。

1. Slopeに削除・初期化・連携解除機能がある場合、二段階確認、対象確認、権限検査、監査記録、復旧手順をコード／UIで確認する。
2. 実データを消さず、テスト用レコード1件を作成し、バックアップ／復元手順を確認する。
3. 親Aのtokenで親Bや全体を対象にする削除要求をローカルで1回試す。

**合格条件:** 子供側や他家庭からの破壊的操作を拒否し、対象範囲を限定する。実端末ワイプ、DB全消去、ランサムウェア実行は行わない。

## 7. 優先順位

1. **P0 個人情報:** PII-01〜09、API-01〜07、API-12、NET-03/07/08、AND-04〜08/12/13。これらは認証・認可・端末保存・ログ・応答本文を横断して最初に確認する。
2. **P0 その他:** IN-07、NET-01/02/04、AND-01〜03。
3. **P1:** QR（API-09〜11, PII-09）、入力境界（IN-01〜06, IN-08〜12）、通信断・版競合（NET-05〜06）、Android OS連携（AND-09〜14）、削除・復旧（PII-10）。
4. **P2:** 可用性（AVL-01〜05）、追加のOS/APIレベル・ネットワーク条件。

各ケースの実施・結果記録が済むまでは合格扱いにせず `BLOCKED: 未検証` とする。API実装の存在だけでPASSにしない。
