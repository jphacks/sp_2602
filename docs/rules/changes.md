# 変更のルール（契約・機能・データ）

「やっぱりこの機能ほしい」は必ず起きる。問題は起きることではなく、**いつ・誰が・どう決めるかが決まっていないこと**。

## 時間帯ごとの扱い（`npm run now` に今どれかが出る）
| 時間帯 | 契約（型・API・画面・DB） | 機能の追加 |
|---|---|---|
| キックオフ〜契約凍結（open） | 自由に変更 | DEMO.md に載せれば追加 |
| 契約凍結〜機能フリーズ（additive） | **追加だけ**。change-request Issue → 同期点で採否 | 同上。DEMO.md に載らないものは Stretch |
| 機能フリーズ以降（frozen） | 変更禁止 | 禁止 |

## 「追加」と「破壊」
- **追加**：新しい型、新しいフィールド（`.optional()` 付き）、新しい API、新しい画面。既存の人の作業を壊さない。
- **破壊**：フィールドの削除・名前変更・型変更・必須化、画面遷移の変更。誰かの作業が壊れる。
- 破壊的な変更は **同期点でしか入れない**。影響する人全員がその場で合意する。

## 手順（additive の時間帯）
1. 欲しくなった人が change-request Issue を立てる（テンプレートあり）。「DEMO.md のどこで必要か」が書けないものは Stretch。
2. 作業は止めない。今の契約のまま、自分のステップを続ける。
3. 次の同期点で lead が採否を決め、採用なら lead が contracts/ を変えて CHANGELOG に1行。
4. 全員が `npm run now` で変更を見て、影響を確認する。
- 例外：デモが成立しない欠陥（型が足りず画面が作れない等）は同期点を待たずに lead へ。

## DB・データ
- 最初に `docs/data-wishlist.md` に欲しいデータを全部書き出し、DEMO.md に映らないものを削る。**削った後のものだけ**を contracts/ に入れる。
- 後から「やっぱりこのデータも」は、上の change-request と同じ扱い（optional フィールドとして追加）。
- ハッカソン中はマイグレーションを作らない。スキーマを変えたら DB は作り直す（シードは contracts/fixtures.ts から）。
