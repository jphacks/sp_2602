### 用語

- **親**: 利用上限・計画・制限対象外アプリの変更権限を持つ利用者。
- **子供**: 実端末の利用状況を収集し、割合表示と利用制限案内の対象になる利用者。
- **テスト期間**: `name`, `startDate`, `endDate` を持つ1件の予定。単一日付ではなく期間で管理する。
- **日別上限**: C10が生成しサーバーへ版付きで保存する「その日の制限対象利用時間の上限（分）」。
- **通常上限**: テスト期間が0件の場合に適用する親の設定値。
- **確定済み過去データ**: 計画の再計算で遡及して変更してはいけない記録・日別上限。

## 2. MVPで達成するユーザー体験

**1つの縦断シナリオ（E2E）** を実機2台で完成させる。

1. 親・子供がC1でログイン。未連携なら、子供がQRを表示し親が読み取る。
2. サーバーで本人・役割・QRトークンを検証し、D2に親子関係を確定保存。両端末が結果を確認する。
3. 親が計画開始日・開始上限S・最終目標G・通常上限を設定する。
4. 親または子供がテスト名・開始日・終了日を登録・編集・削除する。
5. サーバーC10が **将来の日別上限** を生成して版付きで保存する。子供側はC7で取得する。
6. 子供端末C2がAndroidの使用状況から制限対象の利用時間を取得し、C3が使用済み割合と到達状態を算出する。
7. 子供用ホームに **使用済み％と次のテスト**、利用割合画面にゲージを表示する。上限到達時はC4の案内を出す。
8. C8が使用記録をサーバーへ同期し、親が **分単位の実績** をホーム・週間グラフで確認する。
9. 親がC9で制限対象外アプリを変更すると、子供端末へ版付きで反映され、以後のC3/C4で考慮される。

**重要:** Androidは他アプリの強制停止・常時遮断を一般アプリへ無条件には許可しない。MVPの必須合格条件は「上限を検知し、OSが許す範囲で制限案内を表示できること」。実際の遮断能力は権限・OSバージョン・端末で別途実機検証し、保証しない。

## 3. MVPのスコープ

### 3.1 必須（完成判定に含める）

- 親・子供の認証、役割のサーバー検証、QR親子連携、連携状態取得（C1）。
- 子供端末の実際の利用時間取得、使用状況アクセス権限の案内（C2）。
- ホワイトリスト／必須例外を除いた利用時間の集計、使用済み割合・残り割合・到達状態の算出（C3）。
- 上限到達時の案内画面、学習用アプリへの誘導（C4）。
- 子供のホーム・利用割合・テスト期間登録／一覧／編集／削除・設定、親のホーム・計画作成・振り返り・設定の基本UI。
- 子供の割合表示と親の分単位表示、基本の週間実績グラフおよび日別上限計画の参照（C6）。
- 設定・日程・日別上限と版の取得、有効キャッシュ、通信失敗状態（C7）。
- 子供の利用記録をサーバー保存、未送信保持、再送、重複防止（C8）。
- 親だけが変更できる制限対象外アプリ設定と子供への同期（C9）。
- C10の二次関数基準・テスト期間中の維持・途中テスト後の回復・連続テスト・最終目標・過去確定値保護。

### 3.2 MVP後に回すもの

- Androidホームウィジェットの完成（C5）。C5の仕様・表示データ契約は維持し、実装を後回しにする。
- ダークテーマ、複数テーマカラー、高度なアニメーション。
- 半年単位など長期の詳細分析、凝ったアプリ別可視化・レポート。
- 複数家庭／複数子供のための高度な管理画面（**データモデルの将来拡張性とは別**）。
- 完全な端末横断リアルタイム同期や厳密なバックグラウンド時刻保証。

**注意:** 2端末でのMVPデモは「親子関係をDB上で1対1に固定する」承認を意味しない。人数制約は未決定事項として扱う。

| C8 | DB保存・再同期 | 子供端末→サーバーへ送信ID付き実績アップロード。成功分だけ送信待ち解除、再送時は冪等 | 必須 |

### 4.1 C1 — QRのセキュリティと例外

- Google認証の**サーバー検証**と、D2の**親子連携成功**は別の状態。
- QRは子供側が発行し、親側が読み取る。短時間有効・推測困難・原則一回限りのトークンを利用し、認証情報や個人情報をQRへ直接入れない。
- サーバーが親権限、トークン、期限、使用済み、対象子供、既存関係を検証する。
- 親子関係の保存とQR使用済み確定は競合・再送に安全な処理とする。D2保存の**確定後のみ**成功を返す。
- 子供は通知または連携状態再取得で確定結果を確認する。レスポンス消失時はD2を照会し、成功／失敗／不明を区別。
- QR発行・読取・通信・カメラ権限・期限切れ・使用済み・重複連携・キャンセルは失敗系を持つ。
- 親の対象子供データ閲覧は、すべての関連APIでD2による認可を検証する。

### 4.2 C2・C3 — 利用率と異常値

- 制限対象実績を `usedMinutes`、C7由来の当日上限を `limitMinutes` とする。
- `limitMinutes > 0` の場合、実利用率 = `usedMinutes / limitMinutes × 100`。UI用使用済み表示は0〜100%に収め、元の実利用値は保持する。残り表示割合は `max(0, 100 - displayUsedPercent)`。
- `limitMinutes == 0` は有効な上限であり、**到達状態**と扱う。0除算をせず、既存C3図のルールに従い使用済み表示100%、残り0%。
- `limitMinutes < 0` はエラー。上限未設定・通信失敗・実績取得不可はそれぞれ別状態で、勝手に0分と表示しない。
- 制限対象外アプリと安全上の必須例外は、C3の計算およびC4の判定で一貫させる。
- 親へ表示する日別分数と、子供へ表示する割合を区別する。子供側には実使用分数を主要UIとして表示しない。

### 4.3 C7・C8 — データ整合性

- `testPeriods`, `dailyLimits`, `configVersion` を **互いに一致する版** として扱う。キャッシュを異なる版で混合しない。
- `testPeriods.length == 0` は **日別上限未設定と同義ではない**。C10は親の通常上限を適用する。既存C7図の「日程0件＝未設定」という表現はMVP実装時に修正・確認が必要。
- キャッシュが古い場合は、UIに「最新でない可能性」を表示。利用記録取得（C2）と送信待ち（C8）は独立して維持できる。
- C8の送信IDは再試行でも同じIDを維持する。サーバーは二重保存を防止する。
- 一時的な通信／DB障害は送信待ちのまま再試行。恒久的な検証エラーは該当データを隔離し、無限再送しない。

### 4.4 C10 — 日別上限計算

基準曲線（計画開始から最終テスト開始まで）:

\[
B(d)=S-(S-G)u^2,\quad u=\operatorname{clamp}\left(\frac{d-d_0}{D},0,1\right)
\]

- `S`: 開始上限（分）、`G`: 最終目標（分）、`d0`: 計画開始日、`D`: 最終テスト開始までの日数。
- `D > 0` は基準曲線で減少させる。`D = 0`（計画開始日に最終テスト開始）の場合は段階的な減少期間がないため、`S` と `G` が異なっていても最終テスト開始日から `G` を適用する。`D < 0` は不正な設定として受け付けない。
- テスト開始日に基準曲線の値 `Q_i` を目標とし、**開始日・終了日を含むテスト期間中はその上限を維持**。最終テスト期間は `G` を適用し、終了日の翌日から親の通常上限へ切り替える。通常上限が `G` 以下でも値をそのまま適用する。
- 非最終テスト終了後は、FigJamの仕様に従い回復率 `r_i = clamp(0.8(1-u_end^2), 0, 0.8)` を使い、前の回復ピーク `P_i` とテスト上限 `Q_i` から `R_i = Q_i + r_i(P_i-Q_i)` を求める。
- 回復した日から次のテスト開始時の目標まで、**実際の日数に基づいて線形補間**する。連続したテストでは回復しない。
- 中間値は未丸めで処理し、日別上限の確定時に分単位で切り捨てる。
- テスト期間0件では **親の通常上限** を採用する。設定の検証エラーやDB失敗時は前の正式版を保持する。
- 設定変更時は当日分を維持し、翌日から先を再計算する。日本時間の0時を日付境界とする。日別上限は過去の確定値を変更せず、利用実績も再計算しない。
- 最大日次減少幅は設けない。テスト期間の入力が重複・矛盾する場合は入力エラーとして保存しない。
- 入力版の整合性確認と日別上限・計算版の保存を一括で行う。計算または保存が失敗した場合は、前の正常な計画・日別上限・版を維持する。
- **未決定:** 日別上限を何日先まで生成するか。実装中の見本ストアは現状120日先まで生成しているが、期間値はプロダクト仕様として確定していない。

### 5.3 UI共通の必須状態

`loading`／`success`／`empty (記録0件)`／`unknown (取得不可)`／`offline or stale cache`／`validation-error`／`permission-denied` を必要な画面で区別する。テスト日程0件でもホームを使えること。操作を行っただけでは成功と表示せず、サーバー保存の確定を待つこと。

## 6. データとサーバー境界

| ストア | 内容 | アクセス原則 |
|---|---|---|
| D1 利用者 | 認証主体・ロール・識別子 | 認証済み本人／認可された管理処理 |
| D2 家族のつながり | 親ID・子供ID・親子関係 | サーバーが認可し、保存確定後に連携済みを返す |
| D3 テスト日程 | 名前・開始日・終了日・家族／子供紐付け | 親子双方の認可済み編集 |
| D4 日ごとの使用時間 | 子供・日付・アプリ・実績分数・送信ID | 子供が同期、連携済み親だけが閲覧 |
| D6 日別利用上限 | 日付・上限分数・計算版 | C10が保存、C7が取得・配布 |
| D7 制限対象外アプリ | アプリID・対象設定・版 | 親だけが編集。必須例外とは別 |
| D8 利用計画設定 | 計画開始日・S・G・通常上限・版 | 親だけが編集、C10の入力 |

QRの一時トークンの保存先とD2の設計境界は、既存DB方針に合わせて別途確定する。追加のDBテーブルを承認前に確定仕様として記載しない。

| 連携状態取得 | 親子 | 認証済みセッション | `linked` / `unlinked` / 取得不可、対象 |
| 親の計画設定変更 | 親 | 開始日・S・G・通常上限・期待版 | 保存結果・計算版 |
| テスト日程CRUD | 親子 | テストID・名前・開始／終了日・期待版 | 保存結果・C10再計算状態 |
| 日程・上限・版取得 | 親子 | 認証済み対象・既知版 | C7の整合した設定スナップショット |
| 使用実績送信 | 子供 | 日付・アプリ・使用分数・送信ID | 個別保存結果・受理済みID |
| 使用実績閲覧 | 親（認可対象のみ） | 対象子供・期間 | 分単位の実績・取得状態 |
| 制限対象外アプリ更新 | 親 | 子供・アプリ群・設定版 | 保存版・子供端末への適用状態 |

すべての子供ID指定をクライアントから信用せず、サーバーで本人・親子関係・操作権限を検証する。通信・DBエラーと業務上の拒否を分離し、再試行可否を区別する。

## 7. 実装の進め方とチーム分担

**Phase 0 — 既存実装と契約の照合**

- リポジトリ、使用言語、Android UIスタック、サーバーフレームワーク、既存スキーマ・テスト・CIを確認する。
- S2 `back-a/S2-pairing-link` / Issue #10 の契約採否を確認する。契約未承認の認証・QR APIを本実装扱いしない。
- C10の日付確定・変更時点、C4のOS対応方針、親子人数制約を合意する。

**Phase 1 — 実利用時間→割合表示の縦断スライス**

- C2で実端末の利用時間を取得し、C3で割合を計算。
- 既知のテスト設定でC10を検証し、C7形式の上限を使って子供ホーム／利用割合画面へ表示。
- 上限0分、未設定、権限なし、取得不可をテストする。

**Phase 2 — バックエンド・親子連携・保存**

- C1（承認済み認証・QR仕様）、D2、C7・C8・C9の認可・保存・バージョン・再送を接続。
- C10がD3/D8変更後に版付きで確定保存することをテストする。

**Phase 3 — 親用・子供用UI統合**

- Figma「最新」のホーム、計画、日程CRUD、基本グラフ、設定を接続。
- 親に実績分数、子供に割合を表示。C4の上限到達案内を実機で確認。

**Phase 4 — 実機E2E・回帰テスト**

- 親端末 + 子供端末の2台で §2 の全シナリオを実施し、失敗系も確認する。
- 既存フローチャートとUIの差分・制約・残課題を記録する。

**担当分担（推奨）**

- **Backend（担当A）:** C1（サーバー側）、D2、D3/D4/D6/D7/D8、C7・C8・C9、C10、API契約、認可・DB・テスト。
- **Android（担当B）:** Figma UI、C1クライアントQR画面、C2・C3・C4・C6、キャッシュ／送信待ち・同期UI、権限・端末テスト。
- **共同:** API契約確定、データ型と版管理、実機E2E、セキュリティレビュー、PR統合。API契約が未承認なら独自の仕様で双方を固定しない。

## 8. 受け入れ条件（Definition of Done）

| ID | 実証条件 | 検証方法 |
|---|---|---|
| AC-01 | 親・子供がログインし、サーバーがロールを区別する | 実機＋APIテスト |
| AC-02 | 子供QR→親読取→D2確定→両端末が同じ結果を確認 | 実機2台＋APIテスト |
| AC-03 | 期限切れ・使用済み・不正QR・通信断・二重読取で不正連携が発生しない | API単体・競合・失敗テスト |
| AC-04 | 親が開始日・S・G・通常上限を設定、子供は変更できない | UI＋権限/APIテスト |
| AC-05 | 親子双方がテスト期間を追加・編集・削除可能 | UI＋APIテスト |
| AC-06 | C10: テスト0件、通常の減少、D=0、途中テスト回復、連続テスト、最終テスト後の通常上限復帰を計算 | 決定済み日付を使う単体テスト |
| AC-07 | C10: 再計算で確定済み過去値を維持し、失敗時は旧版保持 | DBトランザクションテスト |
| AC-08 | 子供端末で使用状況アクセス権を案内し、実アプリの利用時間を取得 | 実機テスト |
| AC-09 | C3が対象外アプリを除外し、0分上限・未設定・取得不可を正しく区別 | 単体＋実機テスト |
| AC-10 | 上限到達時にC4の案内が出る。OS制限・許可状態も記録 | 実機テスト |
| AC-11 | 子供ホームは使用済み％、親ホームは実績分数と日別上限を表示 | 画面＋API結合テスト |
| AC-12 | 子供の記録が保存され、同じ送信IDの再送で二重登録されない | API＋通信断テスト |
| AC-13 | 親が許可された子供の記録だけを閲覧し、他人の記録は拒否される | 権限/APIテスト |
| AC-14 | C7は設定版混在を防ぎ、通信失敗と古いキャッシュを明示する | 単体・通信断テスト |
| AC-15 | 親のC9変更が子供へ伝わり、未反映・権限拒否を正しく扱う | 2端末結合テスト |
| AC-16 | 日程0件でも、通常上限が設定済みなら利用割合を表示できる | 結合テスト |
| AC-17 | Figma「最新」の親子ナビゲーションと主要画面が利用可能 | 画面レビュー＋操作テスト |

完了は **実機・API・DBテストで確認した項目のみ** 宣言する。`npm run doctor` の型チェックやモック起動だけではMVPの完成を示さない。
